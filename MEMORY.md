# MEMORY.md

Architectural decisions, trade-offs, and gotchas for this project.

## Why `openapi-typescript` instead of `openapi-generator`

- **Before**: Java-based `openapi-generator-cli` with `typescript-fetch` — 33 generated files, ~2500 lines, Java dependency in CI, verbose method names (`loginV1AuthLoginPost`).
- **Now**: `openapi-typescript` + `openapi-fetch` — 1 generated type file, no Java, thin runtime via `createClient<paths>`.
- **Trade-off**: Breaking change for consumers (API surface changed from class-based to function + path-based). Accepted because the SDK was at v0.1.0 with no known external consumers.

## Why Bun instead of npm

- Faster installs, native TypeScript execution (`bun run` without `tsx`), compatible lockfile (`bun.lock`).
- **Trade-off**: `oven-sh/setup-bun@v2` required in CI instead of `actions/setup-node`.
- **Consumer impact**: None. The published package is pure ESM + `.d.ts`. Consumers keep using npm/yarn/pnpm.

## Why named methods (`client.login()`) instead of path-based

- `client.POST("/v1/auth/login", { body: ... })` requires the consumer to know HTTP methods and paths.
- `client.login({ email, password })` provides autocomplete, documentation, and safety — the path and method are encapsulated.
- Generated automatically from the OpenAPI spec's `operationId` field.
- Parameter names are extracted from the spec's JSON schema (body) and parameter definitions (path/query).

## Why flattened parameters

- Path-only and query-only methods accept parameters directly: `client.getConnector({ connector_id })` instead of `client.getConnector({ params: { path: { connector_id } } })`.
- Body + path combos (e.g. `updateConnector`) keep explicit parameter names — the DX tradeoff is worth the clarity.
- Generated in `scripts/lib/build.ts` via the `flatten` flag on `GeneratedMethod`.

## Why `client.ts` is auto-generated from a template

- `scripts/client.ts.tpl` contains the static structure (imports, `createEasySQLClient` function skeleton).
- `scripts/lib/build.ts` and `scripts/lib/extract.ts` generate the dynamic parts (interface, implementation).
- `{{INTERFACE}}` and `{{IMPLEMENTATION}}` placeholders are replaced at generation time.
- Keeps the template readable and the logic testable separately.

## Why the generate script is split into modules

- `scripts/generate.ts` → orchestration only (~50 lines).
- `scripts/lib/extract.ts` → spec parsing, method name derivation, example generation.
- `scripts/lib/build.ts` → TypeScript code generation (interface, implementation, params, args).
- `scripts/lib/docs.ts` → markdown API reference generation.
- `scripts/lib/types.ts` → shared `GeneratedMethod` interface.
- Each module can be understood and tested independently.

## `api-types.ts` and `client.ts` are committed but auto-generated

- Generated by `openapi-typescript` and `scripts/generate.ts` from the API spec.
- Committed so consumers get types on `npm install` without running codegen.
- The CI workflow regenerates them and opens a PR when the spec changes.
- **Do not edit by hand** — changes will be overwritten.

## `docs/API.md` is committed

- Auto-generated markdown reference grouped by category (Auth, Connectors, etc.).
- Shows real parameter names extracted from the spec (e.g. `client.login(email: "...", password: "...")`).
- Committed so it appears in the GitHub repository view. CI regenerates it alongside `api-types.ts` and `client.ts`.

## `repository_dispatch` vs polling

- The EasySQL API repo triggers this repo's workflow via `repository_dispatch` when the spec changes. No cron polling needed.
- `workflow_dispatch` is kept as a manual fallback.
- The API URL is configured via GitHub Actions Variables (`EASYSQL_API_URL`), not hardcoded.

## Retry logic for spec download

- `scripts/generate.ts` retries the spec download 3 times with exponential backoff (1s → 2s → 4s).
- Prevents transient network failures from breaking CI.
- Retries are logged with `⚠` warnings; only the final failure is fatal.

## Manual construction of `api-types.ts`

- The initial `src/api-types.ts` was written by hand (extrapolated from the old `openapi-generator` output) because `api.easysql.net` was unreachable from the development environment.
- It was replaced by the real generated output on the first successful CI workflow run.
- This is no longer an issue — the file is now auto-generated.
